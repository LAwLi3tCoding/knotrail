# 同计划研究复用

Knotrail 在同一 TaskRevision、同一 Plan 内重试节点时，可以保留输入和上下文仍适用的成功研究结果。界面展示每个节点重跑或保留的原因，并在原 Run 下标注复用时间。修改总目标、固定验收或发送新消息后，仍会创建新版本并重新规划。

## 一个具体例子

计划包含三个步骤：A 读取参考说明，B 修改目标文件，C 消费 A 的摘要和 B 的文件产物。用户修改 B 的目标文件后，选择重做 B。

如果 A 的参考说明、实际读取、上下文和摘要均未变化，预览会保留 A，重跑 B、C。执行后的尝试次数为 `1 / 2 / 2`。C 绑定 A 原来的 `producerRunId` 和 `artifactId`，同时绑定 B 第二次运行的新产物。A 的旧 Run、输出摘要和时间不改写，也不会生成一条虚假的模型运行。

选择重试本身不回退工作区。重试节点会读取当前文件；用户在其他文件中保存的修改继续保留。

## 为什么需要独立的研究上下文

过去每个节点都收到完整 Plan、全任务近期 Run 摘要和当前工作区摘要。即使一个节点只声明读取单个文件，也可能使用其他步骤的结果，不能仅凭文件哈希未变就复用。

现在研究请求使用 `research-v1` 上下文：

- 保留任务目标、当前节点定义、检查定义、固定输入预览和回复语言。
- 保留此前会话消息；当前任务版本新增的助手回复由显式产物引用提供。
- 保留本节点或任务级已回答决定，以及实际等待观察。
- 不发送完整 Plan、规划观察、其他节点的运行摘要或动态工作区摘要。

`Run.researchContextDigest` 覆盖上述实际请求的稳定内容及契约版本。输入预览沿用每项最多 4,096 个 UTF-16 代码单元、每 Run 最多 64,000 的限制。后续 `read_input` 的交付范围变化不会改变初始请求摘要。

## 复用资格

全部条件成立时，研究节点才可保留：

| 条件 | 核对方式 |
| --- | --- |
| 当前成功尝试 | NodeState、Run 的 nodeId、attempt、TaskRevision 和 Plan 一致 |
| 纯研究结果 | kind 为 research，无固定检查命令，仅声明文本摘要输出 |
| 上下文记录完整 | 存在 researchContextDigest，按当前输入重建后摘要一致 |
| 读取可追踪 | inputCoverage 为 declared；实际读取完整，工具记录成功；列表、搜索等隐含读取不复用 |
| 文件输入适用 | 重建声明文件绑定，并逐个比较实际读取文件的原字节摘要 |
| 产物引用有效 | 前驱仍是当前成功尝试，产物身份、摘要和内容完整 |
| 输出仍存在 | 每项声明输出恰好有一份非截断且摘要正确的产物 |
| 没有待重新判断的观察 | 外部等待状态仍存在时，保守重跑 |

一次资格检查在递归前驱之间共享本次节点判断结果，使汇总型 DAG 的每个节点上下文只核对一次。下一次准入或检查会重新创建结果表，输入变化不会被旧缓存掩盖。

这些条件证明记录可用于当前局部重试，不证明模型已理解所有输入，也不证明分析结论一定正确。有检查命令、文件产出、旧上下文协议或未知读取的研究仍会重跑。

## 代码调用链

1. `task.previewRetry` 等待当前 Run 停止，保留当前文件。
2. `preview()` 调用 `researchReuseReason()`：目标节点和不合格的已尝试节点进入 affected，再沿 dependsOn 传播。未运行且不受影响的节点保留待办状态。
3. `ImpactPreview.nodeReasons` 提供逐节点解释。`reuseDigest` 绑定保留节点的当前状态、Run 和产物，防止预览后保存证据变化却继续套用旧预览。
4. `task.applyImpact` 重新计算预览。工作区、来源、节点集合、原因或复用证据变化时，要求重新预览。
5. SQLite 事务同时保存节点失效状态、NodeState.reused、node.reused 事件、retryCheckpoint、预览消费和 requestId。实际新 Run 仍在后续调度准入时创建；此处不宣称已实现 T14 的“应用重试与新 attempt 同事务”。
6. `continuationCurrent()` 在尚无本次重试之后的新完成或暂停 Run 时，使用 retryCheckpoint 核对当前工作区。新 Run 完成后恢复其实际收尾基线。
7. `bindInputs()`、后继准入和检查批次继续复核已复用研究。后续编辑如果改变其输入，撤销旧完成资格并阻止用陈旧研究完成验收。

retryCheckpoint 绑定 TaskRevision、Plan、已记录 Run 数量、工作区摘要及已知来源摘要。新消息、目标或检查修订、重新规划及来源失效时会清除；旧版本检查点不能替代新版本的运行依据。

## 界面和导出

影响预览分别显示受影响步骤与保留步骤，每项附具体原因。已复用研究在主对话和右侧规划栏的原 Run 记录中显示核对时间；原始输入、工具记录、产物和运行身份仍可展开。中英文切换只转换界面提示，不翻译命令、文件内容或模型原文。

任务报告新增 Retry and retained research 部分，导出检查点、当前复用标记，以及 `impact.applied`、`node.reused` 的完整事件数据；每个 Run 的输入记录包含 researchContextDigest。SQLite 中的完整任务快照保存同一份 retryCheckpoint 与 NodeState.reused。

## 验证与边界

`tests/core.test.ts` 的 research reuse 回归覆盖原 Run/产物不变、来源变化、未知读取、旧记录、语言变化、产物变化、后续撤销和数据库重建。`tests/ui-workbench.spec.ts` 验证逐节点原因、复用标记、双语和窄屏。

`npm run test:desktop:reuse` 使用真实 Electron → Core → pi → 文件工具链，模型服务为本地协议夹具。它验证运行中 Renderer 重载、未发送草稿、三节点局部重试、原产物消费、用户笔记保留及 App 重启持久化。该结果不能替代真实远端模型或自然任务收益评估。实际结果见 [验证报告](VALIDATION.md)。

跨目标或跨 Plan 的语义复用仍待实现，需要新旧节点含义和证据适用性的显式映射；本次没有放宽跨版本产物绑定规则。
